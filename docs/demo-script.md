# 3 分钟 Demo 讲稿

> 目标：让面试官在 3 分钟内听懂“这不是 LLM 套壳”，并看到可验证的证据。

---

## 0. 演示前检查（30 秒）

- 后端：`http://localhost:8000/health` 返回 `status=ok`
- 前端：`http://localhost:5173` 打开
- 备用：如果网络/LLM 不可用，直接打开 `http://localhost:5173/result?demo=1`
- 准备两个标签页：
  1. 首页
  2. 结果页（示例或真实生成）
- 可选：终端打开 `eval/report.md` 或 `docs/architecture.md`

---

## 1. 开场（0:00–0:30）

> “很多旅行规划 Demo 是‘输入城市 → 一次 LLM 调用 → 返回一段看起来合理的行程’。  
> 它最大的问题不是文笔，而是不可信：景点可能不存在、价格可能编、闭馆日不知道、预算对不上。  
> 我做的是一个只做镇江的版本，核心是：**LLM 只负责选，代码负责事实、约束和预算。**”

---

## 2. 首页（0:30–0:50）

展示：

- 只支持镇江（单城市深度）
- 同行人 / 节奏 / 主题 / 预算
- 没有假进度条，明确“预计 10–20 秒”

可以点一句：

> “这里不追求全国覆盖；先把一个城市的数据、约束、评测做深。”

---

## 3. 一次生成（0:50–1:40）

点击生成，等待时展示：

- 结果页顶部：`trip_id`、`request_id`、`cached`
- **执行轨迹（Trace）**：
  - `load_dataset`：加载 18 个景点/10 家酒店/12 家餐厅
  - `plan`：LLM 只输出 ID，`planner_attempts=1`，Token 数
  - `validate`：闭馆日/三餐/ID/每日时长
  - `budget`：代码算钱
  - `render`：展开事实
- **预算明细**：
  - 四项汇总
  - 每条费用的来源 badge（价格库/默认价）
  - `明细之和 = 总额`
- **每日行程**：
  - 景点 ID 已展开成名称/区域/门票/时长
  - 酒店/餐饮
- **地图**：点位、按天顺序连线

一句话：

> “LLM 没有机会写价格和坐标；它只能从候选 ID 里选。价格是代码按 ID 查的。”

---

## 4. 编辑与重算（1:40–2:10）

- 点“编辑行程”
- 删除一个景点
- 点“保存并重算”
- 展示：预算变化、Trace 重新出现 `validate -> budget -> render`

> “这一步很关键：如果只在前端改，预算就会和明细对不上。所以重算必须回后端，用同一个 Budget 引擎。”

---

## 5. 评测（2:10–2:40）

打开 [eval/report.md](../eval/report.md)，指三行：

| 系统 | 结构合法率 | must-see 覆盖 | ID 幻觉率 |
|---|---:|---:|---:|
| 当前 DAG + LLM | 100% | 100% | 0% |
| 规则保底 | 100% | 54.4% | 0% |
| 单次 LLM | 100% | 100% | 0% |

> “规则保底是零 Token 的确定性基线，它证明校验/预算链路本身是通的；  
> LLM 的增益体现在 must-see 覆盖从 54.4% 到 100%。  
> 另外 26.7% 的 case 超预算，这不是失败，而是我下一步做二次规划的依据。”

---

## 6. 收尾（2:40–3:00）

> “这个项目我最想讲的三件事：  
> 1. 确定性 DAG：代码控制流程，LLM 只做决策节点；  
> 2. Planner 只输出 ID，价格和事实由代码展开；  
> 3. 用评测而不是感觉来证明 LLM 的增益。  
> 我主语言是 Java，这个项目用 Python 是因为 LLM 生态；架构可以映射到 Spring Boot。”

## 常见追问

**Q：这是多 Agent 吗？**  
A：是“多角色 + 确定性编排”。目前生产节点是 Planner；Critic/Narrator 是扩展位。数据获取是工具层，不是三个只会发固定 tool call 的 Agent。

**Q：为什么不用 RAG？**  
A：这个任务是结构化候选 + 约束 + 算钱，不是文档问答。18 个景点用 ID 查表更准。我有独立的 PDF RAG 调优项目，不把 RAG 硬塞进这里。

**Q：为什么不用 LangGraph？**  
A：图是静态的 5 个节点，手写 DAG 能讲清楚拓扑排序、并行、超时、重试、失败隔离，也方便移植 Java。LangGraph 的 checkpoint/streaming 不是刚需。

**Q：怎么保证预算对？**  
A：Planner 只输出 ID；Budget 按 ID 查价格，回写每条明细，`total = sum(lines)` 由 Pydantic validator 强制。

**Q：LLM 编了不存在的景点怎么办？**  
A：Validator 检查 ID 存在性；Planner 内部也会提前查 ID/闭馆日，带错误反馈重试 1 次；仍失败就报错，不返回假行程。

**Q：并发会串数据吗？**  
A：每个请求独立 `TripContext`；Planner 无 history；Redis/内存缓存按 request hash/trip id 隔离。测试里两个不同日期并发不串。

**Q：为什么用 Python？**  
A：LLM/MCP 生态 Python 优先；我的主语言是 Java，架构是接口化的，DAG/Pydantic/FastAPI/Redis/MySQL 都能映射到 Spring Boot。

**Q：这个项目最难的地方？**  
A：不是调通 LLM，而是把“不确定性”关进笼子：ID 契约、Validator、预算恒等、失败语义、评测基线。

## 不要说的话

- “全国实时价格”
- “完全确定性”
- “生产级多 Agent”
- “用户量/并发量很大”（没有真实用户）
- “RAG 让行程更好”（这个项目没走 RAG）

主动说边界，比被问出来更加分。
