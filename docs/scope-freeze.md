# 镇江旅行助手：范围冻结（Day 1）

- **状态**：Frozen
- **冻结日期**：2026-10-27
- **Owner**：项目作者
- **关联文档**：[ADR-001](./adr/001-deterministic-dag.md)

> 这份文档的作用是防止 8 天冲刺期间范围膨胀。  
> 任何新增功能，必须先回答：**它是否服务于“镇江 1–3 天、确定性 DAG、可评测”这三个关键词？**  
> 答案是否定的，就不做。

---

## 1. 一句话产品定义

> **一个只做镇江、把“行程编排”做成确定性 DAG、把 LLM 限制在少数决策节点、并且能解释每一笔预算的旅行规划助手。**

不是“全国旅行规划平台”，不是“通用 Agent 框架”，也不是“RAG 问答机器人”。

---

## 2. 目标用户

- 来镇江玩 **1–3 天** 的游客
- 主要使用 **公共交通 / 步行 / 打车**，少量自驾
- 对 **历史文化、美食、自然、亲子、摄影** 中至少一个主题有偏好
- 有明确预算，或希望知道钱花在哪
- 可能带父母/孩子，需要少走路、少爬坡

---

## 3. In Scope（必须做）

### 3.1 城市与行程

| 项 | 冻结值 |
|---|---|
| 城市 | **镇江**（只做这一个城市） |
| 行程天数 | **1–3 天**（API 可接受 1–7，但产品与评测聚焦 1–3） |
| 覆盖区域 | 京口区、润州区、丹徒区、句容市、丹阳市、扬中市、镇江新区 |
| 行程粒度 | 每天 2–3 个景点 + 1 家酒店 + 早中晚三餐 |
| 交通方式 | 公共交通、步行、打车、自驾 |
| 输出 | 每日行程、预算明细、地图点、Trace、本地贴士 |

### 3.2 主题与人群

- 主题：历史文化、美食、自然、亲子、摄影、宗教
- 人群：solo、couple、family、elderly
- 节奏：relaxed、normal、packed
- 可选约束：预算上限、必去景点、少走路/少爬坡

### 3.3 数据范围（Day 1 冻结）

| 数据 | 数量 | 说明 |
|---|---:|---|
| 景点 | 18 | 含 8 个以上 must-see |
| 酒店 | 10 | 经济型/舒适型/豪华型/民宿 |
| 餐厅 | 12 | 早餐/午餐/晚餐，含本地特色 |
| 交通 | 8 | 镇江站/镇江南站 → 主要区域 |
| 知识卡 | 12 | 文化/历史/美食/诗词，带来源 |

数据规则：

- 每条数据必须有 `source_url` 和 `last_verified`
- 不确定的价格写 `price_note=待核实`，不编造
- 不确定的闭馆日留空，不默认“周一闭馆”
- 坐标允许先 `manual`，Day 2 用高德校准
- ID 稳定：`A001–A018`、`H001–H010`、`R001–R012`、`T001–T008`、`K001–K012`

### 3.4 工程范围

- 代码定义 DAG，LLM 只在 `plan / critique / narrate` 节点内工作
- Planner 只输出 ID，不输出名称、地址、价格、坐标
- Validator + Budget 由代码执行，保证硬约束与预算恒等
- 每次请求无状态，`TripContext` 是唯一状态源
- 每个节点有 Trace：耗时、Token、成本、缓存、降级
- MySQL 存主数据，Redis 做缓存/幂等/限流
- FastAPI 提供 `/api/v1/trips`、`/recalculate`、`/graph`、`/health`
- 前端展示 Trace 时间线与预算来源
- 15 条评测 case + 单次 LLM 基线

## 4. Out of Scope（明确不做）

| 不做 | 原因 |
|---|---|
| 多城市/全国覆盖 | 8 天做不深，数据无法核实 |
| 实时门票/酒店库存/下单 | 需要第三方交易接口，超出范围 |
| 用户登录、支付、订单 | 与核心问题无关 |
| RAG / 向量数据库 | 任务不匹配；已有独立 RAG 项目 |
| Java 重写 | 8 天时间不够；架构可映射到 Spring Boot |
| LangGraph / 复杂 Agent 框架 | 静态图，手写 DAG 更可解释 |
| 管理后台 / 移动 App | 不是面试作品的核心 |
| 多语言 / 国际化 | 不增加工程深度 |
| 实时爬虫 / 大规模数据采集 | 合规与维护成本高 |
| “全国实时价格”宣传 | 不真实，面试会被追问穿 |

## 5. 质量门槛（Definition of Done）

### 5.1 功能

- 输入“镇江 2 天、预算 800、历史文化、公共交通”能返回完整行程
- 行程中每个景点/酒店/餐厅都有真实 ID
- 预算明细相加等于总额
- 超出预算时给出明确提示与二次规划结果
- 工具失败时返回 `degraded`，不返回假行程

### 5.2 工程

- DAG 单测：拓扑顺序、并行、超时、重试、失败隔离、循环检测
- Validator 单测：ID 存在、天数/日期、闭馆日、每日时长
- Budget 单测：命中/未命中、晚数、预算恒等、超预算
- 并发测试：两个请求不串数据
- `pytest -q` 全绿；CI 跑 lint + test + frontend build

### 5.3 作品化

- README 有架构图、Trace 截图、评测表、Quickstart、Limitations
- 90 秒 Demo 视频
- 3 分钟讲稿
- `docs/adr/` 记录关键取舍
- 数据来源与免责声明

## 6. 变更控制

从今天到 Day 7：

1. **不新增功能**，除非同时砍掉一个同等工作量的功能。
2. 任何架构变更，先改 [ADR-001](./adr/001-deterministic-dag.md)，再改代码。
3. 数据字段变更，先改 `schema_zhenjiang.sql` 和 CSV，再改模型。
4. 不删除旧代码，直到新链路通过验收；旧链路保留可回滚。
5. 每天结束更新 `docs/dayN-log.md`：做了什么、AI 生成了什么、我改了什么、明天输入是什么。

## 8. 面试时主动说明的边界

- “这是单城市 MVP，不是全国平台。”
- “价格是参考价，有来源和核实日期，不承诺实时。”
- “行程结构由代码保证，文字描述由 LLM 生成，所以不是‘完全确定性’。”
- “我刻意没有用 RAG：这个任务的结构化数据用 SQL/ID 更准。”
- “我用 Python 是因为 LLM/MCP 生态；架构可以映射到 Spring Boot。”

主动说边界，比被面试官问出来更加分。
